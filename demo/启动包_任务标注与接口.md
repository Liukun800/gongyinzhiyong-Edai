# Demo启动包：任务、材料与接口

版本V0，2026年9月27日。配套可运行流程原型。六份材料由代码构造并按预设事实检查字段与引用，未开展业务访谈或银行人员验证。

## 一、两项任务的标注约定

USE_MATCH：比较同一申请用途范围内的说明与证明。候选为一致、存在明确矛盾、信息不足。一致和矛盾均需两处以上可比原文，缺件时列出已有内容与缺失项；一致不等于真实性认定。

BIZ_CONFLICT：比较同主体、同期间的经营陈述。候选为发现明确矛盾、未发现明确矛盾、无法比较。主体与期间不同先判断可比性，不能把正常时间变化视为矛盾。未发现矛盾只限所给材料。

资料的标注至少包含答案、证据位置、适用范围和不能完成判断的原因。模型答案与后续动作分开；矛盾可被识别，但仍要人工核实。标签和模拟分支位于单独的annotations文件，不进入未来模型输入。

## 二、六份材料

| 编号 | 资金用途任务 | 经营信息任务 | 额外行为 |
|---|---|---|---|
| D01 | 一致 | 未发现明确矛盾 | 两项均待人员复核 |
| D02 | 一致 | 发现明确矛盾 | 经营任务转人工核实 |
| D03 | 信息不足 | 未发现明确矛盾 | 补入订单、产生新版本后可再次核验 |
| D04 | 一致 | 无法比较 | 请求补充同期间经营记录 |
| D05 | 一致（预设复杂分析意见） | 未发现明确矛盾 | 模拟一次复杂分析，不进行外部请求 |
| D06 | 未形成结论 | 未发现明确矛盾 | 对复杂分析注入超时，转人工 |

D05和D06的材料相同，运行条件不同。模拟升级由显式演示情形决定，不能作为模型不确定性或真实模型行为的证据。D06潜在材料答案与本次实际返回状态分别记录。

## 三、接口示例

运行请求：POST /api/cases/D03/run，JSON为：

```json
{"revision": 1}
```

材料新增或编辑请求：POST /api/cases/D03/material：

```json
{
  "revision": 1,
  "document": {
    "id": "order",
    "title": "采购订单",
    "kind": "purpose",
    "subject": "仿真主体A",
    "period": "2026-08",
    "paragraphs": [{"id": "p1", "text": "订单关联申请SIM-001，采购标的为生产用钢材。"}]
  }
}
```

服务返回的新revision为2，下一次运行请求须使用2。复核请求发往POST /api/runs/{运行返回的id}/review：

```json
{
  "revision": 2,
  "task_id": "USE_MATCH",
  "action": "confirm",
  "reason": "已对照用途说明和采购订单，两处表述一致。"
}
```

confirm只用于待复核任务；resolve记录待人工核实任务的处理结论；correct记录纠正；supplement请求补充；refer继续人工处理。resolve与correct需提交有效的corrected_answer。信息不足或无法比较的人工结果仍为待补充。

每条任务返回id、name、answer、score、calibration、status、action、reason、evidence、analysis、source、review等字段。score当前为null；source为fixture_simulator或unsupported_input。真正模型适配时需定义独立来源名称，保留实际调用信息，不能沿用预设来源冒充推理。

## 四、首版验收

- 六种情形均返回两项任务，按预设处理路径运行。
- 两项任务状态独立；申请汇总保留待处理数量。
- 证据引用与运行时材料快照逐字对应；编辑后保留旧快照。
- 补件产生新版本；当前版本重跑前不允许复核旧结果。
- 人工确认、纠正和核实记录保留依据，不删除原始模拟判断。
- 自定义内容不沿用预设答案；明确转人工。
- 模拟服务超时不会返回成功，不循环请求。
- 页面显示模拟状态、实际调用为0，不展示虚构置信度或收益。

验收结果见qa/browser-results.json及测试输出；这属于软件功能验收，不属于模型性能或真实银行业务验证。
