## 第一遍演示顺序

1. 选择D01，点击“运行核验流程”。查看两项任务、原文证据及“待复核”状态。模型分数为空，真实模型请求为0。
2. 选择D02运行。经营材料存在同期间冲突，该任务进入人工核实。
3. 选择D03运行。用途任务提示缺件；点击“补入演示采购订单”，材料变成新版本，再次运行后显示用途一致。
4. 在D03查看旧运行，确认旧结果仍存在且不能直接复核。选择最新运行，通过“记录复核”填写处理依据。
5. 选择D04，查看不同月份材料为什么进入待补充，而非被当成同期间矛盾。
6. 选择D05，展示预设复杂分析意见及三处证据；选择D06，展示模拟超时后转人工。
7. 编辑任意预设材料并重跑。新内容未命中仿真样例时，系统明确返回待人工核实，不把旧答案当成新预测。点击“恢复预设材料”可建立新的原始材料版本，历史记录不删除。
8. 点击“导出记录”保存当前样例的材料、运行快照与处理历史。

## 数据与接口

data/cases.json只包含仿真材料及演示补件；data/annotations.json单独保存预设答案和分支，用于流程模拟。engine.py通过材料内容指纹确认其与预设版本完全匹配，材料改变则保留为待人工处理。真实模型适配时不应将annotations作为模型输入或将这六份演示材料当作未见测试集。

runtime/demo.sqlite3保存本地状态。每次运行保存材料快照；补件或编辑增加版本；复核保留原始答案，并通过事件记录每次人工动作。这里只实现演示级留痕，不能声称具备生产级不可篡改审计。

主要API：

| 方法与地址 | 内容 |
|---|---|
| GET /api/health | 模式、模型加载状态、当前页面写入令牌 |
| GET /api/cases | 样例列表 |
| GET /api/cases/D01 | 当前材料、运行与处理事件 |
| POST /api/cases/D01/run | 指定revision运行模拟 |
| POST /api/cases/D01/material | 提交revision与document，编辑或补件 |
| POST /api/cases/D01/reset | 指定revision恢复预设材料为新版本 |
| POST /api/runs/{run_id}/review | task_id、revision、action、reason及可选corrected_answer |

写入采用JSON和X-Demo-Token头，令牌从本地health取得。修订号过期、复核历史运行返回409；缺少令牌或来自其他网页的写入返回403。前端例子见static/app.js，业务接口及字段说明见“启动包_任务标注与接口.md”。
